# Applied Pay payout matcher - draft, PROPOSE ONLY

The matcher parses Applied's settlement email plus xlsx, reads QBO receipt/reversal JEs and existing Trust 3021 deposits, and returns review buckets. It does not post to QBO or EZLynx. `qbo_client.py` reads QBO via GET/query but rotates its refresh token into Secret Manager; credential write-back must stay within the owner-approved QBO read scope. It does not authorize QBO postings or EZLynx writes.

## Bank status and double-count controls

An Applied email is a scheduled settlement notice, not proof that the deposit cleared the bank. `email_parse.parse` labels it `status: scheduled`. QBO's existing deposits are also **not** bank-clearing proof. The matcher only makes a new `ready` proposal when an independently verified `cleared_bank_deposits` entry matches account `10002 Trust Checking WF (3021)`, amount and payout/next-day date, plus an exact `verified_payout_ref`, `verification_source: bank_record` and nonempty `bank_transaction_id`. A `status: cleared` flag without independent source and payout binding is insufficient. No bank-source integration is included in this PR; until one exists, the daily report will correctly say `scheduled_unlanded` or `unmatched`, not `ready`.

An existing QBO deposit may be marked `already_posted` only if its `groups` are exactly the matched JE IDs and line totals tie. With missing PSP-bound EZLynx notes, a unique exact deposit group whose receipt JEs also tie to every settlement line by amount, customer and date is `already_posted_needs_review` instead, never final reconciliation or a new proposal. A same-amount QBO deposit containing unrelated JEs stops. Neither bucket creates another proposal. Unknown, ambiguous, missing or wrong-account JEs stop. A completed bank deposit may still need a person to inspect business context before any manual posting; the report is advice, not authorization.

## Fee and payable review

For new proposals the runner must check EZLynx notes for each payment, attach source-bound evidence (`ezlynx_note_check` with status `checked`, source `ezlynx`, the same PSP reference, note IDs and notes), and stop short of READY when that check is absent. An MBR or agency-fee note triggers fee review; a payable note (such as Shirley's example) is held as a payable, not relabeled as a fee. Conflicting fee/payable notes stop. Explicit premium and fee components can show a suggested split only when a bound EZLynx fee note exists and sums tie. Fee-only, small unexplained and note-flagged payments remain human review; no fee or payable account is guessed. The current PR has **no EZLynx note-fetch adapter**; until one is built and tested, new deposits cannot safely become READY.

## Planned unattended workflow and client account notes (not implemented)

Carlo wants the Applied Pay pull-and-match flow fully automated and a dated factual note on the client's EZLynx account **after independently verified bank clearing**. A reconciled batch email, a scheduled settlement, an Applied portal label, and an existing QBO deposit are not proof of clearing. The runner must distinguish settlement reconciliation from actual cleared funds. No note should say "money cleared" solely on a reconciled or scheduled batch; if bank evidence is absent or conflicting, hold the note and report the reason. Current code does not fetch a bank feed, fetch EZLynx notes, or write account notes; this section is a plan, not permission to enable writes now. The note-write implementation route (supported API versus controlled UI plan) and rollout are separate decisions after review of #554's merge/deployment path. Do not treat this PR as a scheduled service.

Done criteria for unattended operation:

- Retrieve each Accounting@ Applied "Batch Settlement Details" message with its matching xlsx, preserve message/attachment identifiers, parse all rows, and stop if line totals do not tie to the stated batch deposit. Give each transfer ID one durable processing record and surface parser/source errors rather than silently skipping a batch.
- Read current QBO receipts, reversals and existing Trust 3021 deposits. Match each payment to exactly one source-bound client/account using PSP reference, receipt and identity evidence; hold ambiguous names, duplicate amounts/receipts, wrong-account or already-grouped JEs, mixed clients, returns and fee/payable questions. QBO posting remains out of scope and proposal-only.
- Obtain an independent bank transaction record for Trust 3021 showing **cleared**, exact amount and transfer binding (`verified_payout_ref`, `verification_source: bank_record`, nonempty `bank_transaction_id`); verify relevant dates and uniqueness. A generic same-amount deposit, pending/scheduled bank item, bank email, QBO entry or Applied notice does not satisfy this. Stop on duplicate, changed, reversed or disputed evidence. The bank adapter and its source-of-truth semantics need design and testing before unattended release.
- For each payout line destined for a client note, double-verify the specific EZLynx account using two independent, source-backed identity links, not just a similar name or two fields copied from one record. For example, tie the Applied PSP/receipt reference to a policy number in its payment source, and separately verify that policy number and named insured against the selected EZLynx account; where a client has multiple accounts, resolve the exact account ID and check both links independently. If either link is missing, conflicts, points to another account, or leaves multiple plausible accounts, write no note and escalate to a human. Verify fee/payable/reversal context too. Never write a batch-total note on every client account; use that client's settled line amount only when it can be distinguished from mixed-client batches and any returned or withheld amount. A bound note check and account lookup are required; unverified mappings and fees remain review items.
- After the bank-clearing and client binding gates, prepare a dated, factual note with the cleared date, that client's verified settled amount, Applied transfer ID, source transaction reference, and any relevant receipt reference. Do not claim a policy is paid, coverage is active, the carrier has funds, or fees are settled merely because Applied's bank transfer cleared. The note must identify the evidence reviewed without copying secret tokens, raw bank records or another client's details into the account. The exact wording and write authority must be confirmed for the chosen EZLynx account-note surface before enabling automatic writes.
- Make note writes idempotent by a durable key including bank transaction ID, transfer ID, source PSP/receipt, client account and event type. Read back an existing note before writing; retry safely after partial failures; never duplicate a note or mark completion before readback. Corrections or reversals need an explicit factual follow-up workflow, not silent editing or deletion. Alert a human on any ambiguous account, missing clearing proof, note write failure or changed bank status.
- Design one box-hosted, code-reviewed runner and timer, with locking, replay/backfill policy, observability, secret handling and stop/recovery behavior; do not install or enable it as part of this spec update. Coordinate retirement or deduplication of the current weekday task before any box timer goes live. Synthetic tests must cover no note on scheduled/reconciled-only batches, source-bound cleared notes, two independently backed account identifiers, multiple accounts for one client, conflicting identity evidence, mixed-client amounts, wrong account, duplicate/reversed bank events, and retries. Run a read-only shadow against real data before enabling writes; roll out separately with the exact account-note and service permissions confirmed.

Run synthetic safety checks with `python3 -m unittest applied_pay.tests.test_safety`.
